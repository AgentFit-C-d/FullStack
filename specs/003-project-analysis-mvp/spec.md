# Feature Specification: 프로젝트 생성과 분석 시작 MVP

**Feature Branch**: `003-project-analysis-mvp`

**Created**: 2026-10-13

**Status**: Ready for planning

**Input**: User description: "로그인 사용자만 프로젝트 생성 가능, 프로젝트 이름 저장, 기획서 파일 또는 Markdown 입력 저장, 분석 시작 버튼 작동, 분석 상태가 PROCESSING으로 표시됨, 내 역할 저장, 개발환경 저장, 프로젝트 정보 화면에서 저장된 값 다시 불러오기, 새로고침해도 값이 남아 있음, 기본 테스트 통과"

## Clarifications

### Session 2026-10-13

- Q: 프로젝트 생성 시 기획서 파일과 Markdown은 반드시 하나만 입력하게 할까요? → A: 형식은 달라도 프로젝트당 기획서는 하나만 저장한다.
- Q: 한 프로젝트의 개발환경은 여러 항목을 함께 저장해야 할까요? → A: 여러 개발환경 항목을 저장하며, 한 줄 또는 쉼표로 입력한 중복 없는 항목을 최대 30개, 항목당 최대 200자로 보존한다.
- Q: 기획서 파일은 어떤 종류와 최대 크기까지 받을까요? → A: PDF·Markdown 파일 또는 직접 입력 텍스트를 지원한다. 파일은 최대 10 MiB(10,485,760 bytes), PDF는 최대 100쪽이며, 파일에서 추출한 텍스트와 직접 입력은 각각 100,000 Unicode code points 이하여야 한다. 초과분은 자동으로 자르지 않고 거부하며, 한 분석 요청에는 입력 하나만 사용한다.
- Q: 이미 `PROCESSING`인 프로젝트에서 분석 시작을 다시 누르면 어떻게 할까요? → A: 새 분석을 만들지 않고 기존 `PROCESSING` Attempt와 프로젝트 상태를 유지한 채 `409 Conflict`를 반환한다. 화면은 이를 일반 오류가 아닌 “분석이 이미 진행 중입니다. 완료될 때까지 기다려 주세요.” 안내로 표시한다.
- Q: 기획서 원문 파일·직접 입력 내용을 새로고침 뒤에도 다시 보여주기 위해 저장할까요? → A: 원문, 프로젝트 메타데이터, 분석 결과를 저장하고 재조회한다. 원문은 프로젝트 소유 데이터로만 관리하며 Audit·일반 로그에는 복제하지 않는다.
- Q: 역할·개발환경은 분석·사용자 확인 전, 처음 프로젝트 생성 화면에서 바로 저장할까요? → A: 프로젝트 생성 시 역할과 기술·런타임 목록을 즉시 저장한다.
- Q: “내 역할”은 어떤 형식으로 받을까요? → A: `FRONTEND`, `BACKEND`, `FULL_STACK`, `AI`, `DESIGNER` 중 하나를 선택한다.
- Q: 역할의 세부 담당 업무(`responsibilities`)도 이번 MVP에서 받을까요? → A: 담당 업무는 이번 MVP에서 저장하지 않는다.
- Q: 개발환경은 어디까지 받을까요? → A: 기술·런타임 목록만 저장한다.
- Q: 개발환경 목록에 같은 이름이 다시 들어오면? → A: 중복을 자동으로 제거하고 하나만 저장한다.
- Q: 만든 뒤 프로젝트 이름·역할·개발환경을 수정해서 다시 저장할 수 있을까? → A: 생성 뒤에도 같은 프로젝트 정보를 수정해 저장할 수 있다.
- Q: 기획서를 바꿔 다시 분석하면 기존 분석 이력은? → A: 기존 분석 이력은 보존하고 새 분석을 생성한다.
- Q: 분석 시작 버튼이 이번 단계에서 실제 분석 완료·실패까지 처리할까? → A: 이번 MVP는 분석 시작 접수와 `PROCESSING` 표시까지만 구현한다. 결과 생성은 후속 단계에서 연결하되 결과 저장·재조회 요구는 보존한다.
- Q: 문서의 동시 제한을 이번 MVP부터 전부 적용할까? → A: 활성 분석은 프로젝트당 1건, 사용자당 1건, 서버 전체 2건으로 제한한다.
- Q: 직접 입력 기획서는 어떤 형식으로 처리할까? → A: 직접 입력은 UTF-8 `text/plain` 일반 텍스트로 처리한다. Markdown은 파일 입력(`text/markdown`)일 때만 지원한다.
- Q: 원문과 이전 입력 버전은 언제까지 보관할까? → A: 원문 파일·직접 입력·추출문·근거 인용문은 분석의 성공·실패·시간 초과·취소·비정상 종료 직후 삭제한다(보관 기간 0일). 분석 이력과 비원문 메타데이터·결과는 보존한다.
- Q: 사용자·서버 동시 제한을 넘겼을 때의 응답은? → A: 같은 프로젝트의 진행 중 재요청만 `409 Conflict`이며, 사용자당 1건 또는 서버 전체 2건 제한 초과는 `429 Too Many Requests`다.
- Q: 분석이 완료되지 않은 MVP에서 `PROCESSING`을 어떻게 종료할까? → A: 분석 시작부터 600초가 지나면 `FAILED`로 전환하고 원문 데이터를 즉시 삭제한다.
- Q: 프로젝트 생성 요청의 응답이 끊긴 뒤 재시도되어도 중복 생성되지 않게 하려면? → A: 클라이언트가 `Idempotency-Key`를 보내고 서버가 동일 키의 생성 결과를 재사용한다.
- Q: `PROCESSING` 분석이 있는 프로젝트를 삭제하면? → A: 활성 분석이 있는 동안 프로젝트 삭제를 `409 ANALYSIS_ACTIVE_PROJECT_DELETE_FORBIDDEN`으로 거부하고, Attempt·원문·admission 상태를 변경하지 않는다.
- Q: 실제 결과 생성이 없는 MVP에서 원문 삭제의 종료 범위는? → A: 이번 MVP의 terminal 상태는 600초 시간 초과 `FAILED/TIMEOUT`만 구현·검증한다. 후속 성공·실패·취소·비정상 종료 경로도 같은 원문 삭제 처리를 반드시 재사용한다.
- Q: “시간 초과 뒤 즉시 삭제”는 어느 주기로 보장할까? → A: 만료 정리 작업은 최대 10초 간격으로 실행한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 프로젝트 정보와 기획 입력 저장 (Priority: P1)

로그인한 사용자는 프로젝트 이름, 자신의 역할, 기술·런타임 목록, PDF·Markdown 파일 또는 직접 입력 일반 텍스트 중 하나의 기획 입력을 함께 제출해 프로젝트를 만들 수 있다. 원문은 분석을 수행하는 동안에만 보관하며, 프로젝트 정보 화면에서는 지속 보관되는 메타데이터와 저장된 값을 확인할 수 있다.

**Why this priority**: 프로젝트와 원천 기획 입력이 없으면 이후 분석을 시작할 대상이 없으므로 MVP의 가장 중요한 흐름이다.

**Independent Test**: 로그인한 테스트 사용자가 유효한 프로젝트 정보를 한 번 제출한 뒤 프로젝트 정보 화면에서 프로젝트 메타데이터·역할·기술·런타임을 확인하면 이 사용자 스토리가 동작한 것으로 본다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자가 필수 프로젝트 정보를 입력한 상태에서, **When** 프로젝트 생성을 완료하면, **Then** 프로젝트가 생성되고 이름·단일 역할·기술·런타임 목록·기획 입력이 함께 저장된다.
2. **Given** 사용자가 PDF 또는 Markdown 기획서 파일을 선택한 상태에서, **When** 프로젝트를 저장하면, **Then** 파일 원문은 분석 종료 전까지만 보호해 보관되고 이름·크기·형식 메타데이터는 프로젝트 정보로 보존된다.
3. **Given** 사용자가 직접 입력 일반 텍스트를 작성한 상태에서, **When** 프로젝트를 저장하면, **Then** 입력 원문은 분석 종료 전까지만 보호해 보관되고 `text/plain` 형식과 문자 수 메타데이터는 보존된다.
4. **Given** 기획 입력 방식이 PDF·Markdown 파일 또는 직접 입력 텍스트 중 하나인 상태에서, **When** 프로젝트를 저장하면, **Then** 프로젝트당 하나의 기획서만 저장되고 선택한 방식의 값만 조회된다.
5. **Given** 사용자가 역할과 기술·런타임 목록을 입력한 상태에서, **When** 프로젝트를 저장하면, **Then** 역할은 허용된 단일 선택값으로, 런타임은 중복 없는 목록으로 저장된다.

### User Story 2 - 저장된 프로젝트 정보 복원 (Priority: P1)

사용자는 프로젝트 정보 화면을 다시 열거나 브라우저를 새로고침해도 자신이 저장한 프로젝트 이름, 역할, 기술·런타임 목록, 기획서 메타데이터와 이용 가능한 분석 결과를 다시 볼 수 있다. 종료된 분석의 원문은 다시 표시되지 않는다.

**Why this priority**: 새로고침 후 값이 사라지면 사용자는 저장 성공 여부를 신뢰할 수 없고 분석을 이어갈 수 없다.

**Independent Test**: 프로젝트 저장 후 화면을 새로고침하고 같은 프로젝트를 다시 조회해 저장 전 값과 동일한지 비교한다.

**Acceptance Scenarios**:

1. **Given** 프로젝트가 저장되어 있는 상태에서, **When** 사용자가 프로젝트 정보 화면을 다시 열면, **Then** 저장된 이름·역할·기술·런타임 목록·기획서 메타데이터·분석 결과가 동일하게 표시된다.
2. **Given** 프로젝트 정보 화면에 저장된 값이 표시된 상태에서, **When** 사용자가 브라우저를 새로고침하면, **Then** 프로젝트 이름·역할·기술·런타임 목록·기획서 메타데이터가 유지된다. 종료된 분석의 원문은 표시하지 않는다.
3. **Given** 다른 사용자의 프로젝트 식별자를 알고 있는 상태에서, **When** 현재 사용자가 프로젝트 정보를 요청하면, **Then** 프로젝트 정보가 노출되지 않고 접근 거부 결과가 반환된다.
4. **Given** 프로젝트 소유자가 저장된 정보를 수정한 상태에서, **When** 다시 저장하면, **Then** 같은 프로젝트의 현재 정보가 갱신되고 새로고침 후 갱신값이 표시된다.

### User Story 3 - 분석 시작과 상태 표시 (Priority: P2)

사용자는 저장된 프로젝트에서 분석 시작을 누를 수 있고, 시작이 접수되면 프로젝트 정보 화면에서 분석 상태가 `PROCESSING`으로 표시되는 것을 확인할 수 있다.

**Why this priority**: MVP의 다음 행동을 명확하게 만들고, 실제 분석 결과가 준비되기 전에도 시스템이 요청을 접수했다는 피드백을 제공한다.

**Independent Test**: 저장된 프로젝트에서 분석 시작을 실행한 뒤 상태를 조회해 `PROCESSING`인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자의 저장된 프로젝트가 분석 가능한 상태일 때, **When** 사용자가 분석 시작을 실행하면, **Then** 분석 요청이 접수되고 상태가 `PROCESSING`으로 전환된다.
2. **Given** 분석 상태가 `PROCESSING`인 상태에서, **When** 사용자가 프로젝트 정보 화면을 새로고침하면, **Then** `PROCESSING` 상태가 유지되어 표시된다.
3. **Given** 저장된 기획 입력이 없는 프로젝트에서, **When** 사용자가 분석 시작을 실행하면, **Then** 분석은 시작되지 않고 사용자가 보완해야 할 입력을 알 수 있는 검증 결과가 반환된다.
4. **Given** 프로젝트의 분석 상태가 `PROCESSING`인 상태에서, **When** 사용자가 분석 시작을 다시 실행하면, **Then** 새 분석은 생성되지 않고 기존 Attempt와 상태를 유지한 채 `409 Conflict`가 반환되며 화면에는 “분석이 이미 진행 중입니다. 완료될 때까지 기다려 주세요.”가 표시된다.
5. **Given** 다른 프로젝트에서 같은 사용자의 분석이 `PROCESSING`인 상태에서, **When** 사용자가 새 분석을 시작하면, **Then** 새 분석은 생성되지 않고 `429 Too Many Requests`와 사용자 동시 제한 안내가 반환된다.
6. **Given** 서버 전체에서 두 건의 분석이 `PROCESSING`인 상태에서, **When** 사용자가 새 분석을 시작하면, **Then** 새 분석은 생성되지 않고 `429 Too Many Requests`와 서버 동시 제한 안내가 반환된다.
7. **Given** 분석 시작 후 600초가 지난 상태에서, **When** 만료 처리가 실행되면, **Then** Attempt는 `FAILED`로 전환되고 원문·추출문·근거 인용문은 즉시 삭제된다.
8. **Given** 이전 분석이 종료된 프로젝트에서, **When** 소유자가 새 기획 입력을 제출해 다시 분석을 시작하면, **Then** 새 분석 이력과 입력 메타데이터 버전이 생성되고 기존 분석 이력·입력 메타데이터·결과는 보존된다. 이전 원문은 보존하지 않는다.

### User Story 4 - 인증과 기본 입력 검증 (Priority: P1)

로그인하지 않은 사용자는 프로젝트를 생성하거나 분석을 시작할 수 없고, 로그인한 사용자의 요청도 필수값과 허용된 입력 범위를 벗어나면 저장되지 않는다.

**Why this priority**: 프로젝트와 기획 입력은 사용자 소유 데이터이므로 인증·소유권 경계가 기능 자체보다 우선한다.

**Independent Test**: 비로그인 요청과 잘못된 입력 요청을 각각 실행해 저장·분석 상태 변경이 발생하지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 인증되지 않은 사용자가, **When** 프로젝트 생성 또는 분석 시작을 요청하면, **Then** 요청이 거부되고 프로젝트 데이터가 생성·변경되지 않는다.
2. **Given** 로그인한 사용자가 빈 프로젝트 이름 또는 허용 한도를 넘는 값을 제출한 상태에서, **When** 저장을 요청하면, **Then** 유효성 오류가 반환되고 부분 저장이 발생하지 않는다.
3. **Given** 사용자가 타인의 프로젝트에 대해 분석 시작을 요청한 상태에서, **When** 요청을 실행하면, **Then** 요청이 거부되고 타인의 분석 상태가 변하지 않는다.

### Edge Cases

- 프로젝트 이름이 비어 있거나 공백만 포함되거나 100자를 넘는 경우 저장하지 않으며, 초과분을 자동으로 자르지 않는다.
- PDF·Markdown 파일과 직접 입력 텍스트가 동시에 입력되거나 모두 비어 있는 경우 저장하지 않고, 사용자가 기획서 하나의 형식을 선택하도록 안내한다.
- PDF·Markdown 파일이 10 MiB(10,485,760 bytes)를 넘거나 PDF가 100쪽을 넘으면 저장하지 않는다.
- 파일에서 추출한 텍스트 또는 직접 입력 텍스트가 100,000 Unicode code points를 넘으면 저장하지 않으며, 초과분을 자동으로 자르지 않는다.
- 한 분석 요청에는 하나의 기획 입력만 사용한다.
- 기술·런타임 항목은 빈 값을 저장하지 않고, 중복은 자동으로 제거한다. 30개를 넘거나 항목당 200자를 넘으면 저장하지 않는다.
- `PROCESSING` 상태인 프로젝트에 분석 시작을 다시 요청하면 새 분석을 만들지 않고 기존 Attempt와 상태를 유지한 채 `409 Conflict`를 반환한다.
- `PROCESSING` 상태의 프로젝트를 새로고침하거나 다른 화면으로 이동한 뒤 다시 열어도 서버에 저장된 상태를 기준으로 표시한다.
- 저장 직후 네트워크 응답이 끊겨도 같은 `Idempotency-Key`로 재시도하면 중복 프로젝트를 생성하지 않고 최초 생성 결과를 반환해야 한다.
- 존재하지 않거나 삭제된 프로젝트를 조회·분석하려는 요청은 프로젝트 정보를 노출하지 않는다.
- 서버 전체의 활성 분석이 2건이거나 같은 사용자의 활성 분석이 1건이면 새 분석을 시작하지 않고 `429 Too Many Requests`를 반환한다.
- `PROCESSING` Attempt가 있는 프로젝트 삭제는 `409 ANALYSIS_ACTIVE_PROJECT_DELETE_FORBIDDEN`으로 거부하며, Attempt·원문·admission 상태는 변하지 않는다.
- 이번 MVP에서 구현하는 terminal 상태인 600초 시간 초과 뒤에는 최대 10초 안에 원문 파일·직접 입력·추출문·근거 인용문을 삭제한다. 후속 성공·실패·취소·비정상 종료도 같은 삭제 처리를 재사용해야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 인증된 사용자만 프로젝트를 생성할 수 있도록 해야 한다.
- **FR-002**: 시스템은 프로젝트 이름을 필수값으로 저장하고, 공백 이름과 100자를 넘는 이름을 거부하며 초과분을 자동으로 자르지 않아야 한다.
- **FR-003**: 시스템은 프로젝트당 현재 기획 입력 하나를 분석 종료 전까지만 보호해 저장해야 한다. 이번 MVP에서 구현하는 600초 시간 초과 terminal 처리에서는 원문·추출문·근거 인용문을 최대 10초 안에 삭제해야 하며, Audit·일반 로그에 복제해서는 안 된다. 후속 성공·실패·취소·비정상 종료 경로도 동일한 삭제 처리를 재사용해야 한다.
- **FR-003a**: 시스템은 원문을 제외한 기획 입력 메타데이터(형식, 파일명·크기 또는 문자 수), 분석 결과와 분석 이력을 보존하고 소유자가 재조회할 수 있게 해야 한다. 이번 MVP는 결과 생성이 아니라 분석 시작 접수와 `PROCESSING` 상태 표시까지만 구현한다.
- **FR-004**: 시스템은 PDF·Markdown 파일과 직접 입력 텍스트가 동시에 제출되거나 모두 누락될 때 저장을 거부하고, 사용자가 기획서 하나의 형식을 선택하도록 안내해야 한다.
- **FR-004a**: 시스템은 PDF·Markdown 파일을 최대 10 MiB(10,485,760 bytes)로 제한하고, PDF는 최대 100쪽으로 제한해야 한다.
- **FR-004b**: 시스템은 파일에서 추출한 텍스트와 직접 입력 일반 텍스트를 각각 최대 100,000 Unicode code points로 제한하고, 초과분을 자동으로 자르지 말고 저장을 거부해야 한다.
- **FR-004c**: 시스템은 한 분석 요청에 하나의 기획 입력만 사용해야 한다.
- **FR-005**: 시스템은 프로젝트 생성 시 사용자의 역할을 `FRONTEND`, `BACKEND`, `FULL_STACK`, `AI`, `DESIGNER` 중 하나로 저장하고 다시 조회할 수 있어야 한다.
- **FR-005a**: 시스템은 역할의 세부 담당 업무를 이번 MVP에서 저장·조회하지 않아야 한다.
- **FR-006**: 시스템은 프로젝트 생성 시 사용자가 입력한 기술·런타임 목록을 프로젝트 정보로 저장하고 다시 조회할 수 있어야 한다.
- **FR-006a**: 시스템은 기술·런타임 항목을 줄바꿈 또는 쉼표로 구분해 입력받고, 빈 값은 제외하며 중복은 자동으로 하나만 남긴 최대 30개 항목을 저장해야 한다.
- **FR-006b**: 시스템은 개발환경 항목 하나가 200자를 넘거나 총 항목이 30개를 넘으면 저장을 거부하고 사용자가 수정할 수 있는 검증 결과를 반환해야 한다.
- **FR-007**: 시스템은 프로젝트 정보 화면에서 프로젝트 이름·기획서 메타데이터·역할·기술·런타임 목록·분석 상태·이용 가능한 분석 결과를 다시 조회할 수 있도록 해야 한다. 종료된 분석의 원문·추출문·근거 인용문은 반환해서는 안 된다.
- **FR-008**: 시스템은 소유자가 프로젝트 이름·역할·기술·런타임 목록을 수정해 같은 프로젝트에 저장하고, 새로고침·재조회 후에도 갱신된 값을 반환해야 한다.
- **FR-008a**: 시스템은 `PROCESSING` Attempt가 있는 프로젝트의 삭제를 `409 ANALYSIS_ACTIVE_PROJECT_DELETE_FORBIDDEN`으로 거부하고, 활성 Attempt·원문·admission 슬롯을 변경해서는 안 된다.
- **FR-009**: 시스템은 인증된 소유자만 자신의 프로젝트 정보를 조회하거나 해당 프로젝트의 분석을 시작할 수 있도록 해야 한다.
- **FR-010**: 시스템은 유효한 소유자가 분석 시작을 요청하면 분석 상태를 `PROCESSING`으로 저장하고 조회 결과에 표시해야 한다.
- **FR-010a**: 시스템은 분석 시작 시점부터 600초의 기한을 기록하고, 최대 10초 간격의 만료 정리 작업으로 기한을 넘긴 `PROCESSING` Attempt를 `FAILED/TIMEOUT`으로 전환한 뒤 원문·추출문·근거 인용문을 삭제해야 한다.
- **FR-011**: 시스템은 기획 입력이 없는 프로젝트의 분석 시작을 거부하고, 저장·상태 변경 없이 보완 가능한 오류를 반환해야 한다.
- **FR-012**: 시스템은 `PROCESSING` 상태에서 반복된 분석 시작 요청에 새 분석을 만들지 않고 기존 Attempt와 프로젝트 상태를 유지한 채 `409 Conflict`를 반환해야 한다.
- **FR-012a**: 화면은 `PROCESSING` 상태에서 받은 `409 Conflict`를 일반 오류로 표시하지 않고 “분석이 이미 진행 중입니다. 완료될 때까지 기다려 주세요.”로 안내해야 한다.
- **FR-012b**: 시스템은 활성 분석을 사용자당 1건, 서버 전체 2건으로 제한하고 한도를 넘는 요청에는 새 Attempt를 만들지 않고 `429 Too Many Requests`를 반환해야 한다.
- **FR-012c**: 시스템은 종료된 분석 뒤 재분석을 시작할 때 새 Attempt와 기획 입력 메타데이터 버전을 만들고 기존 분석 이력·입력 메타데이터·결과를 보존해야 한다. 이전 원문·추출문·근거 인용문은 보존해서는 안 된다.
- **FR-013**: 시스템은 프로젝트 생성 요청에서 `Idempotency-Key`를 받아 동일 키의 순차·동시 재시도에는 최초 생성 결과를 재사용하고 중복 프로젝트를 만들지 않아야 한다.
- **FR-014**: 시스템은 프로젝트 생성·수정·조회·분석 시작·600초 시간 초과 처리의 성공·거부·유효성 오류·동시 제한·멱등 재시도를 기본 자동 테스트로 검증해야 한다.

### Key Entities

- **Project**: 인증된 사용자가 소유하는 작업 단위. 이름, 소유자, 단일 역할, 기술·런타임 목록, 현재 기획서, 생성·수정 시점과 분석 상태를 가진다.
- **Planning Input**: 프로젝트의 현재 분석 원천 입력. PDF·Markdown 파일 또는 UTF-8 `text/plain` 직접 입력 중 사용자가 선택한 한 가지의 원문은 분석 종료 전까지만 보관하고, 메타데이터만 지속 보존한다.
- **Planning Input Revision**: 재분석을 시작할 때 생성되는 기획 입력 메타데이터의 불변 버전이다. 이전 Analysis Attempt가 참조한 형식·파일명·크기 또는 문자 수는 보존하지만 원문·추출문·근거 인용문은 보존하지 않는다.
- **Analysis Attempt**: 특정 프로젝트와 기획 입력 버전에 대한 분석 시작 요청과 현재 상태를 나타낸다. 새 재분석은 별도 Attempt로 보존하며 MVP에서는 최소한 `PROCESSING` 상태를 표현한다.
- **Analysis Result**: 분석이 완료되는 단계에서 Attempt에 연결되는 결과다. 결과 생성은 후속 단계지만, 저장·재조회와 이력 보존은 이 기능의 데이터 요구사항이다.
- **Project Ownership**: 프로젝트를 생성·조회·분석할 수 있는 인증 사용자와 프로젝트의 관계다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 유효한 로그인 사용자의 프로젝트 생성 테스트 100%에서 프로젝트 이름·기획서 메타데이터·단일 역할·여러 기술·런타임 항목이 저장되고 조회된다. 원문은 분석 종료 전까지만 존재한다.
- **SC-002**: 비로그인 또는 타인 프로젝트 요청 테스트 100%에서 프로젝트 생성·조회·분석 상태 변경이 발생하지 않는다.
- **SC-003**: 프로젝트 저장·수정 후 새로고침·재조회 테스트 100%에서 저장된 프로젝트 정보와 기획서 메타데이터가 원래 입력 또는 수정값과 동일하게 표시된다. 종료된 분석의 원문은 재조회되지 않는다.
- **SC-004**: 유효한 분석 시작 요청의 100%가 사용자에게 `PROCESSING` 상태로 표시된다.
- **SC-005**: 기획 입력 누락·`PROCESSING` 중 분석 재요청·10 MiB(10,485,760 bytes) 초과 파일·100쪽 초과 PDF·100,000 Unicode code points 초과 텍스트 테스트 100%가 저장 없이 검증 오류 또는 중복 방지 결과를 반환한다. 같은 프로젝트 재요청은 기존 상태를 유지한 `409 Conflict`와 안내 문구를, 사용자·서버 동시 제한은 `429 Too Many Requests`를 반환한다.
- **SC-006**: MVP 기본 자동 테스트가 모두 통과하고, 핵심 사용자 여정의 성공·실패 시나리오가 각각 최소 1개 이상 검증된다.
- **SC-007**: 프로젝트·사용자·서버 동시 제한 테스트 100%에서 각각 1건·1건·2건을 넘는 새 분석 Attempt가 생성되지 않는다. 프로젝트 중복은 `409`, 사용자·서버 제한은 `429`를 반환한다.
- **SC-008**: 이번 MVP의 600초 시간 초과 테스트 100%에서 최대 10초 안에 Attempt가 `FAILED/TIMEOUT`으로 전환되고 원문·추출문·근거 인용문이 남지 않으며 메타데이터·분석 이력만 유지된다.
- **SC-009**: 같은 `Idempotency-Key`로 프로젝트 생성을 순차·동시 재시도한 테스트 100%에서 하나의 프로젝트만 생성되고 최초 생성 결과가 반환된다.

## Assumptions

- 기존 GitHub OAuth 기반 로그인과 프로젝트 소유권 경계를 재사용한다.
- 기획서 원문·추출문·근거 인용문은 분석 종료 전까지만 보호해 저장한다. 이번 MVP는 600초 시간 초과 처리에서 최대 10초 안에 삭제하며, 후속 성공·실패·취소·비정상 종료 경로도 동일한 삭제 처리를 재사용한다. 프로젝트 메타데이터·분석 이력·결과는 보존하며 Audit·일반 로그에는 원문을 복제하지 않는다.
- MVP에서 분석 결과 생성과 AI 모델 품질은 범위에 포함하지 않으며, 분석 시작 접수와 `PROCESSING` 상태 표시까지만 다룬다. 결과가 생성되는 후속 단계에서는 결과·이력 저장 요구를 적용한다.
- 기획 입력은 형식이 달라도 한 프로젝트에 하나의 원천 기획서만 사용한다. PDF·Markdown 파일 또는 UTF-8 `text/plain` 직접 입력을 지원하며, 파일은 최대 10 MiB(10,485,760 bytes), PDF는 최대 100쪽, 파일에서 추출한 텍스트와 직접 입력은 각각 최대 100,000 Unicode code points로 제한한다. 초과분은 자동으로 자르지 않으며, 한 분석 요청에는 입력 하나만 사용한다.
- 역할은 프로젝트 생성 시 단일 enum으로 저장하며 담당 업무는 받지 않는다. 기술·런타임은 한 줄 또는 쉼표로 구분한 여러 항목을 중복 제거해 최대 30개, 항목당 최대 200자로 보존하며, 별도 추천 기능은 후속 범위다.
- 역할·기술·런타임 목록은 기준 문서의 후속 단계 순서와 달리 사용자의 제품 결정에 따라 프로젝트 생성 시 저장한다.
- 동시 제한은 프로젝트당 1건, 사용자당 1건, 서버 전체 2건의 활성 분석에 적용한다. 같은 프로젝트의 진행 중 재요청은 `409`, 사용자·서버 제한 초과는 `429`다.
- 분석 Attempt는 시작 시점부터 최대 600초이며, 시간 초과 시 `FAILED`로 종료되고 원문 데이터를 삭제한다.
- 프로젝트 생성의 네트워크 재시도는 `Idempotency-Key`로 중복을 방지한다.
- `PROCESSING` Attempt가 있는 프로젝트는 삭제하지 않는다. 활성 Attempt가 끝난 뒤의 기존 프로젝트 삭제 경계는 `002-project-ownership`을 따른다.
- 프로젝트 정보 화면은 저장된 서버 값을 다시 조회하는 화면이며, 브라우저 메모리만으로 값을 유지하는 방식은 완료로 인정하지 않는다.
- 삭제·버전 충돌·AI 결과 저장은 `002-project-ownership`과 후속 기능의 기존 경계를 따른다.

## Out of Scope

- 실제 AI 분석 결과 생성과 완료·실패 상태의 상세 UX
- 기획서 전체 텍스트의 AI 추출·질문·확정 처리
- 프로젝트 공유, 협업자 권한, 공개 링크
- 담당 업무 입력과 OS·클라이언트·인증 준비·설치 목록을 포함한 전체 환경 프로필
- 파일 편집기와 외부 저장소 연동

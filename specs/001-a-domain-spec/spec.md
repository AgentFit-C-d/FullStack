# Feature Specification: A 도메인 요구사항

**Feature Branch**: `not-created (before_specify hook 없음; 명세 디렉터리: 001-a-domain-spec)`

**Created**: 2026-10-06

**Status**: Draft

**Input**: 사용자 요청에 따른 풀스택 A 전체 요구사항 명세. 이 문서는 이후 데이터 모델,
ERD, 기능별 명세의 기준이며 그 설계나 구현 자체는 포함하지 않는다.

**Role Confirmation**: 외부 Full Stack A PRD는 A가 인증·프로젝트·저장·서버 통합 역할이라는
역할명 확인에만 사용한다. 제품 요구사항, 우선순위, 완료 지표, Client, 인증 방식은 최신
`AgentFit_AB_1차통합_개발기준.pdf`와 헌장을 기준으로 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 프로젝트 생성과 문서 분석 시작 (Priority: P1)

인증된 프로젝트 소유자는 프로젝트를 만들고 하나의 문서 또는 직접 입력을 분석에 제출한다.
시스템은 접수 사실과 분석 진행 상태를 보여 주며, 분석 결과가 준비되어도 이를 사용자 확정
기획으로 표시하지 않는다.

**Why this priority**: 분석할 프로젝트와 입력이 없으면 A의 이후 기획·Review·추천 흐름이
시작될 수 없다.

**Independent Test**: 소유자가 새 프로젝트에서 허용된 입력을 제출한 뒤 초안 또는 안전한
실패 상태를 확인할 수 있는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 소유자의 새 프로젝트, **When** 허용된 문서 하나를 제출하면, **Then** 문서 요약과
   분석 시도가 기록되고 분석 상태가 사용자에게 보인다.
2. **Given** 분석이 성공한 프로젝트, **When** AI가 기획 후보를 반환하면, **Then** 결과는 DRAFT로
   남고 CONFIRMED 또는 추천 입력으로 자동 승격되지 않는다.
3. **Given** 다른 사용자의 프로젝트 또는 제한을 넘는 입력, **When** 분석을 요청하면, **Then**
   요청은 거부되고 기존 초안·확정 기획은 바뀌지 않는다.

---

### User Story 2 - 기획 검토와 명시적 확정 (Priority: P1)

프로젝트 소유자는 DRAFT의 10개 기획 값을 검토하고, AI 후보에 대해 수락·수정·거절·보류를
표시한 뒤 전체 기획을 명시적으로 확정한다. 사용자는 AI 제안과 자신의 최종 선택이 다른
경우에도 그 차이를 이해할 수 있어야 한다.

**Why this priority**: 확정 기획은 B의 추천과 이후 설정의 기준이므로, AI 결과를 사용자 의사로
바꾸지 않는 것이 핵심 가치다.

**Independent Test**: 후보가 있는 DRAFT를 소유자가 전체 확인하여 CONFIRMED와 확인 이력이
생기는지, 필수 상충 응답이 없으면 저장되지 않는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 현재 DRAFT와 예상 버전, **When** 소유자가 10개 값을 전체 확인하면, **Then**
   CONFIRMED와 불변 확인 사건이 함께 생성되고 프로젝트 기준 버전이 증가한다.
2. **Given** 필수 상충 후보, **When** 사용자가 필요한 행동을 누락하면, **Then** 전체 저장은
   거부되고 기존 확정값과 보류 정보는 유지된다.
3. **Given** 같은 기획을 다른 요청이 먼저 바꾼 상황, **When** 이전 버전으로 확인을 저장하면,
   **Then** 충돌로 알리고 자동 병합이나 최신값으로의 자동 치환은 하지 않는다.

---

### User Story 3 - 개발자·개발환경 원천 정보 관리 (Priority: P1)

프로젝트 소유자는 자신의 역할·책임·숙련도와 운영체제, Client, 런타임, 인증 준비, 설치한
구성 요소를 입력하거나 갱신한다. 사용자는 모름과 명시적으로 없음이 서로 다르게 보존되기를
기대한다.

**Why this priority**: 추천은 기획뿐 아니라 사용자가 실제로 선언한 역할·환경을 기준으로
이루어지며, 추측한 설치 정보는 잘못된 추천을 만든다.

**Independent Test**: 역할과 환경을 각각 저장하고, 한쪽의 변경이 다른 쪽의 값·버전을
덮어쓰지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 환경 목록이 UNKNOWN인 프로젝트, **When** 사용자가 빈 설치 목록을 명시하면,
   **Then** KNOWN인 빈 목록으로 저장되어 UNKNOWN과 구별된다.
2. **Given** 같은 이름으로 정규화되는 런타임 또는 설치 항목, **When** 중복 값을 제출하면,
   **Then** 임의 병합하지 않고 사용자가 정리하도록 거부한다.
3. **Given** 환경 정보, **When** Secret 또는 실제 인증값이 포함된 입력을 제출하면, **Then**
   해당 값은 저장·응답·감사 기록에 포함되지 않는다.

---

### User Story 4 - 재분석과 Review 실패에도 기존 정보 보존 (Priority: P2)

소유자는 문서를 다시 분석하거나 현재 기획의 구조화 Review를 요청할 수 있다. 실패, 기한
초과, 늦은 응답, 대상 변경이 발생해도 이전의 성공한 DRAFT, CONFIRMED, Review와 보류 정보는
사라지지 않아야 한다.

**Why this priority**: 외부 AI 호출은 실패하거나 늦어질 수 있으므로, 한 번의 실패가 사용자가
확정한 정보를 잃게 해서는 안 된다.

**Independent Test**: 분석 또는 Review를 시작한 뒤 대상 기획을 변경하거나 실패 응답을
주입하여, 이전 성공 상태가 유지되고 오래된 결과가 적용되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 CONFIRMED와 성공한 Review, **When** 재분석이 실패하면, **Then** 실패는
   안전한 상태로 기록되지만 기존 정보는 유지된다.
2. **Given** 분석 시작 뒤 DRAFT가 변경된 경우, **When** 이전 분석 결과가 늦게 도착하면,
   **Then** 결과를 적용하지 않고 현재 DRAFT를 보존한다.
3. **Given** Review 대상 ID 또는 버전이 달라진 경우, **When** 오래된 Review가 성공해도,
   **Then** 활성 Review로 교체하지 않는다.

---

### User Story 5 - B·AI·Frontend와 연결되는 A 기준 제공 (Priority: P2)

사용자는 확정 기획과 현재 역할·환경을 바탕으로 추천을 받는다. A는 B와 AI가 필요한 정보를
일관된 기준 시점으로 제공하되, B·AI·Frontend가 A의 원천 데이터를 직접 수정하지 못하게
한다.

**Why this priority**: 추천의 이유와 재현 가능성은 어떤 사용자 확정·환경·검토를 기준으로
했는지에서 나온다.

**Independent Test**: 확정 사건과 역할·환경이 있는 프로젝트의 snapshot을 만들고, 기준 버전이
바뀌면 이전 추천 기준이 최신으로 위장되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 CONFIRMED, **When** B가 추천 기준을 요청하면, **Then** 확정 사건, 기획,
   역할·환경 버전, 유효 Review와 보류 정보가 같은 기준 시점으로 전달된다.
2. **Given** B의 질문에 대한 사용자 답변, **When** 답변이 A의 원천 기획·역할·환경을 바꾸면,
   **Then** 소유권·기준 버전을 다시 확인한 뒤 관련 A 상태와 Audit이 함께 저장된다.
3. **Given** AI가 후보를 반환했지만 사용자 확정이 없는 경우, **When** Frontend가 상태를
   표시하면, **Then** 제안·미정·확정 상태를 구분하며 확정으로 표시하지 않는다.

---

### User Story 6 - 감사 가능한 변경과 프로젝트 삭제 (Priority: P3)

프로젝트 소유자는 자신의 변경이 안전하게 기록되며, 프로젝트를 명시적으로 삭제했을 때
관련 A/B 데이터가 다시 생성되지 않기를 기대한다.

**Why this priority**: 추천·설정 전에 신뢰할 수 있는 이력과 삭제 경계가 있어야 개인 프로젝트
데이터를 안전하게 운영할 수 있다.

**Independent Test**: 성공 변경과 삭제를 각각 수행하고, 관련 Audit의 존재와 삭제 뒤 지연
분석·Review 결과가 거부되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 사용자 확정 같은 성공 변경, **When** 저장이 완료되면, **Then** 상태 변경·버전·
   Audit이 모두 존재하거나 모두 존재하지 않는다.
2. **Given** 다른 사용자의 프로젝트, **When** 삭제를 요청하면, **Then** 요청은 거부되고 어떤
   데이터도 삭제·복원되지 않는다.
3. **Given** 삭제가 완료된 프로젝트, **When** 이전 AI 응답이 늦게 도착하면, **Then** 결과는
   저장되지 않고 프로젝트를 다시 만들지 않는다.

---

### Edge Cases

- 입력 문서가 허용 형식·크기·쪽 수·문자 수 제한을 넘는 경우 기존 상태를 바꾸지 않고 거부한다.
- AI 응답에 금지된 기획 키, 알 수 없는 후보 ID, 필수 판단 누락, 잘못된 근거 위치가 있으면
  빈 성공 응답으로 보정하지 않고 계약 오류로 처리한다.
- UNKNOWN, 명시적 빈 목록, null 값, 빈 배열을 서로 같은 값으로 변환하지 않는다.
- 동시 저장, 재시도, 기한 초과, 프로젝트 삭제와 지연 응답의 조합에서도 이전 확정값을
  덮어쓰지 않는다.
- 실패 진단 원문을 일반 로그·Audit·사용자 응답으로 복사하지 않는다.

## Requirements *(mandatory)*

### 상태 표기와 문서 근거

각 요구사항은 다음 상태 중 하나로 표시한다.

- **확정**: 개발기준의 PM 결정 또는 A 채택으로 명시되어 구현 시 준수해야 하는 업무 규칙.
- **제안**: 구현 전 담당자 합의, 계약 버전, fixture, 시험이 필요한 설계 방향. 구현 완료를
  의미하지 않는다.
- **미결정**: 문서와 현행 코드로 확정할 수 없어 임의로 결정하지 않는 항목.

문서 근거의 `p.`는 `Docs/AgentFit_AB_1차통합_개발기준.pdf`의 페이지 번호다.

### Functional Requirements

- **FR-A-001 — 프로젝트와 소유권 관리**
  - **상태**: 확정. **근거**: 2절 p.4-5, A1 p.9, 13절 p.35.
  - 시스템은 인증된 사용자 소유의 프로젝트를 만들고 목록·상세 조회·변경·명시적 삭제할 수
    있어야 한다. 프로젝트는 현재 사용자 단계와 공유 기준 버전을 가진다.
  - 입력은 인증 주체와 프로젝트 식별자이며, 결과는 소유자에게만 보이는 프로젝트 상태다.
    다른 사용자·다른 프로젝트의 ID·근거·이벤트 참조는 거부한다.
  - **수용 기준**: 소유자는 자신의 프로젝트를 조작할 수 있고, 타인의 읽기·쓰기·삭제는
    상태 변화 없이 거부된다.

- **FR-A-014 — 인증 주체와 프로젝트 소유권 통합**
  - **상태**: 인증·소유권 통합 책임은 확정, 로그인 제공자와 세션 흐름은 미결정.
    **근거**: 2절 p.4의 `identity / project` A 책임, A1 p.9의 사용자 소유 프로젝트,
    13절 p.35의 인증·소유권 삭제 검사.
  - A는 로그인 자체를 화면에서 구현한다는 뜻과 별개로, 서버가 인증 주체를 식별하고 그
    주체를 프로젝트 소유자 및 Audit 행위자와 연결하도록 통합해야 한다. 분석·기획·환경·
    삭제를 포함한 모든 프로젝트 작업은 인증 주체와 소유권을 검증한 뒤에만 수행한다.
  - 로그인 제공자, 가입·로그아웃 화면, 세션 또는 토큰 방식, USER/SESSION의 상세 모델은
    최신 개발기준에 정의되지 않았으므로 이 명세가 선택하지 않는다.
  - **수용 기준**: 인증 주체를 확인할 수 없거나 소유자가 아닌 요청은 프로젝트 데이터·근거·
    Audit 대상에 접근하거나 상태를 바꾸지 못한다. 인증 주체가 확인된 요청은 변경 기록의
    행위자와 연결된다.

- **FR-A-002 — 기획 DRAFT와 CONFIRMED 관리**
  - **상태**: 확정. **근거**: A2-A4 p.9-10, 5절 p.16-18.
  - 시스템은 `project_name`, `project_type`, `domain`, `database`, `deployment`, `frontend`,
    `backend`, `ai`, `features`, `external_integrations`의 10개 기획 값과 출처·근거·미정
    상태를 관리해야 한다. `purpose`, `target_users`, `constraints` 및 별칭은 수집·질문·저장·
    추천 근거에서 제외한다.
  - DRAFT는 분석·편집 중 기획이고 CONFIRMED는 사용자의 명시적 전체 확인 후의 현재 기획이다.
    빈 문자열, 범위를 벗어난 키, 잘못된 근거, 소유권이 다른 문서 근거는 거부한다.
  - **수용 기준**: AI 또는 클라이언트가 제안만 보낸 경우 CONFIRMED가 생기지 않으며, 각
    알려진 문서 값에는 유효한 위치 근거가, 사용자 값과 미정 값에는 올바른 출처 상태가 남는다.

- **FR-A-003 — 문서 접수와 분석 시도 관리**
  - **상태**: 확정. **근거**: 2절 p.5, A5-A6 p.11, 19-20절 p.44-45.
  - 시스템은 프로젝트마다 PDF, Markdown, 직접 입력 중 하나를 접수하고 최소 메타데이터와
    분석 시도를 관리해야 한다. 입력 상한은 요청당 하나, 10 MiB, PDF 100쪽, 텍스트
    100,000 code points다.
  - 분석 시도는 진행·성공·실패와 시작 기준, 기한, 안전한 오류만 구분한다. 성공 결과는 현재
    기준과 일치할 때만 DRAFT에 반영하며, 저장 성공 후에만 저장된 DRAFT를 결과로 알린다.
    읽을 수 없음·부분 추출·계약 불일치는 정상 전체 분석으로 표시하지 않는다.
  - **수용 기준**: 허용 범위를 넘는 입력·소유자 불일치·기한 초과는 기존 DRAFT와 CONFIRMED를
    바꾸지 않는다. `requestId`만으로 중복 저장 방지를 주장하지 않는다.

- **FR-A-004 — AI 후보와 Review 보존**
  - **상태**: 확정인 업무 경계와 제안인 상세 수신 구조가 혼재한다. **근거**: A12-A13 p.14,
    10-12절 p.29-32.
  - 시스템은 대상 기획 ID·버전에 연결된 Review와 후보를 보존하고, 모델 원판정, 서버의
    후속 판단, 근거·상충 근거, 질문·사유를 사용자 행동과 분리해야 한다.
  - AI가 제안하는 값·판단은 자동 확정할 수 없다. 미등록 후보, 상충된 판단, 활성 계약의
    필수 필드 누락은 성공한 항목 0개로 바꾸지 않고 계약 오류로 처리한다.
  - **수용 기준**: 대상이 바뀐 뒤 도착한 Review는 현재 활성 Review가 되지 않으며, 성공한
    Review 항목이 0개인 경우도 실패·미실행과 구분된다.

- **FR-A-005 — 사용자 확인과 후보 행동**
  - **상태**: 확정. **근거**: A11 p.13, 5절 p.16-18, AI-02 p.30.
  - 전체 확인은 10개 기획 값, 예상 프로젝트 버전, 현재 DRAFT 식별·버전, 필요한 Review와
    후보 행동을 검증해야 한다. 신규 행동은 ACCEPT, EDIT, REJECT, DEFER만 허용한다.
  - 성공 시 시스템은 CONFIRMED, 불변 확인 사건, 프로젝트 버전, 실제 사용자 행동, 필요한
    보류 투영, Audit을 함께 저장한다. DEFER는 해결 완료가 아니며, 이전 보류를 새 행동으로
    복제하거나 조용히 지우지 않는다.
  - **수용 기준**: 필수 상충 후보의 응답 누락·중복 후보·다른 Review·행동과 최종값의 모순은
    전체 저장을 거부한다. 정상 후보를 생략한 전체 확인은 가짜 행동을 만들지 않는다.

- **FR-A-006 — 재분석·Review 경쟁과 기존 정보 보존**
  - **상태**: 확정. **근거**: 6절 p.19-20, AI-03 p.30-31, 인수 사례 M03-M06·M29-M30 p.38-39.
  - 시스템은 분석과 Review 시작 순서를 추적하고, 더 늦은 응답·변경된 대상·기한 초과·삭제된
    프로젝트의 결과를 현재 상태에 적용하지 않아야 한다.
  - 분석 또는 Review 실패는 안전한 실패 상태로 남기되, 기존 CONFIRMED, 성공한 Review,
    확정 사건, 보류 정보를 덮어쓰거나 삭제해서는 안 된다.
  - **수용 기준**: 같은 프로젝트의 동시 요청에서 최신 유효 기준만 적용되며, 실패가 빈 성공
    또는 자동 최신화로 표현되지 않는다.

- **FR-A-007 — 개발자 프로필 관리**
  - **상태**: 확정. **근거**: A7 p.12, 9절 p.27.
  - 시스템은 프로젝트당 개발자 역할, 책임 목록, 숙련도를 관리하고 독립 버전으로 변경을
    추적해야 한다. 미작성 프로필과 명시적으로 빈 책임 목록을 구분한다.
  - 역할 변경은 환경 정보를 덮어쓰지 않으며, 허용되지 않은 역할·형식·크기 제한 위반은
    거부한다.
  - **수용 기준**: 역할 저장과 환경 저장을 동시에 수행해도 두 값과 두 버전이 각각 보존된다.

- **FR-A-008 — 개발환경과 설치 정보 관리**
  - **상태**: 확정. **근거**: A8-A10 p.12-13, A15 p.15, 9절 p.27-28.
  - 시스템은 사용자 진술로서 운영체제, Client, 구성 상태, 런타임, 인증 준비, 설치 구성 요소를
    관리해야 한다. 실제 설치·호환성 검증 결과로 추정하거나 Secret을 저장해서는 안 된다.
  - 목록의 UNKNOWN과 KNOWN 빈 목록을 구분하고, 정규화 후 중복 이름은 자동 병합하지 않는다.
    환경과 하위 목록 변경은 하나의 환경 기준 버전에 반영한다.
  - **수용 기준**: 설치 구성 요소의 Catalog 힌트만으로 설치 또는 호환이 확정되지 않으며,
    같은 정규화 이름의 서로 다른 버전 입력은 정리 요청으로 거부된다.

- **FR-A-009 — B·AI·Frontend로의 기준 정보 제공**
  - **상태**: 확정. **근거**: 2절 p.4-5, 9절 p.27-28, 11절 p.32.
  - A는 B에 확정 사건·확정 기획·현재 역할·환경 버전·유효 Review·승계된 보류 정보를 일관된
    기준 시점으로 제공해야 한다. B는 이를 추천에 사용하되 A 원천값을 직접 소유·변경하지
    않는다.
  - A는 AI에 허용된 기획·대상·실제 입력만 전달하고, AI 결과의 계약·대상·소유권·버전을
    검증한다. Frontend는 A를 통해서만 상태를 표시·변경하며 제안·확정·미정을 구분한다.
  - **수용 기준**: 현재 가변 값으로 과거 확정 snapshot을 재구성하지 않으며, AI와 B는
    데이터 저장소를 직접 변경하지 않는다.

- **FR-A-010 — 계약과 오류 의미의 일치**
  - **상태**: 확정. **근거**: 2절 p.4, 10-12절 p.29-34, 헌장 원칙 VI.
  - A가 공개하거나 내부에 제공하는 정보는 정상·실패 fixture, 버전, nullable 규칙, 길이·
    목록 한도, 안전한 오류 의미와 함께 합의되어야 한다. 공개 경로와 요청·응답의 정확한
    이름은 미결정이며 이 명세가 임의로 확정하지 않는다.
  - **수용 기준**: 계약 불일치·파싱 실패·AI 장애·저장 실패는 정상 빈 결과나 사용자 확정으로
    변환되지 않는다.

- **FR-A-011 — 동시성, 트랜잭션, Audit 원자성**
  - **상태**: 확정. **근거**: 6절 p.19-20, 9절 p.28, 13절 p.35.
  - 프로젝트를 변경하는 A/B 작업은 소유권·예상 버전·현재 기준을 확인하고 프로젝트 기준으로
    직렬화한다. 외부 호출은 저장 트랜잭션 밖에서 수행하며, 반환 후 다시 기준을 검사한다.
  - 사용자 확인, 역할·환경 저장, B 질문 답변에 따른 원천값 저장, 성공한 업무 사건은 관련
    버전·상태·Audit과 함께 전부 저장되거나 전부 롤백되어야 한다.
  - **수용 기준**: 충돌 요청은 부분 저장 없이 거부되고, 성공 변경에 Audit이 없거나 Audit만
    남는 상태가 생기지 않는다.

- **FR-A-012 — 최소 Audit과 실패 진단 보관**
  - **상태**: Audit 요구는 확정, 실패 진단의 세부 암호화·운영 방식은 제안/NOT_RUN.
    **근거**: A14 p.15, 11절 p.31-32, 13절 p.35, 20절 p.45.
  - 시스템은 성공·거부·실패를 추적할 최소 Audit을 남기되 원문·Secret·원시 AI 응답을
    넣어서는 안 된다. 최종 분석 실패에서 실제로 수신한 원인 응답만 별도 진단 대상으로
    다룬다.
  - 정상 성공·복구 성공·미수신·B 실패·별도 Review 실패를 분석 실패 원문 보관 대상으로
    확대하지 않는다. 보관 상한 7일은 정책이며, 물리 삭제·복제본·백업 증명 전에는 운영
    기능 완료로 표시하지 않는다.
  - **수용 기준**: 진단이 필요한 실패와 그렇지 않은 실패가 구분되고, 어떤 경우에도 진단
    원문이 일반 로그나 Audit으로 복사되지 않는다.

- **FR-A-013 — 통합 삭제와 지연 결과 차단**
  - **상태**: 삭제 요구는 확정, 정확한 물리 FK·삭제 순서는 제안. **근거**: 13절 p.35,
    인수 사례 M20·M40 p.38-39.
  - 시스템은 인증·소유권·명시적 삭제 확인 후 프로젝트의 기획·분석·Review·역할·환경·진단·
    Audit 및 연결된 B 종속 데이터를 일관되게 제거해야 한다. USER, SESSION, 공용 Catalog,
    이미 사용자가 내려받은 파일은 프로젝트 삭제 대상이 아니다.
  - 삭제 뒤의 분석·Review·추천·Export 결과는 저장·복원·재생성할 수 없다.
  - **수용 기준**: 삭제 완료 뒤 해당 프로젝트의 종속 상태를 조회할 수 없고, 지연 응답이
    도착해도 새 프로젝트나 관련 행이 만들어지지 않는다.

### Full Stack A 확장 책임 범위

Full Stack A는 단순히 분석 결과를 저장하는 담당이 아니다. 사용자가 서비스에 들어와 자신의
프로젝트를 다시 찾고, 분석·수정·확정한 뒤 B의 추천·설정 흐름으로 안전하게 넘어가기까지의
서버 측 기준을 통합한다.

- **인증 통합과 접근 경계**: 최신 개발기준이 A에 배정한 identity/project 경계에서 인증
  주체를 프로젝트 소유자·Audit 행위자와 연결하고, 모든 직접 요청에도 소유권을 적용한다.
  로그인 제공자·화면·세션 방식은 이후 결정이지만, 인증을 서버 업무와 연결하는 일은 A의
  해야 할 일이다.
- **프로젝트 수명주기**: 생성·상태 관리·수정·삭제를 관리하고, 삭제 뒤 지연 응답의 복원을
  막는다.
- **분석 통합**: 입력 제한과 안전한 외부 AI 전달 경계를 검사하고, 분석 시도·진행·성공·실패·
  재시도·직접 작성의 서버 상태를 관리한다.
- **사용자 데이터의 진실성**: AI 초안, 사용자 수정, 미정, 실제 확정, Review, 보류를 구분해
  저장하고 오래된 요청이 확정값을 덮어쓰지 못하게 한다.
- **공통 저장·보안**: 최소 문서 메타데이터, Profile, 개발자·환경 정보, Audit, 제한된 실패
  진단을 소유하며 원문·추출문·Secret을 일반 저장소와 로그에서 격리한다.
- **협업 통합**: Frontend에는 안전한 상태·오류·충돌 복구 의미를 제공하고, AI에는 허용된
  입력과 종료 경계를 제공하며, B에는 소유권·확정 기준·승인 유효성·삭제 경계를 제공한다.
- **후속 Config 연결**: B의 추천·권한·Config 판정을 복제하지 않는다. 다만 B 결과가
  프로젝트 소유권, Audit, 삭제, 현재 기준과 연결되도록 공통 서버 규칙을 제공한다.

  검증 기록은 현재 사업 기능의 검증 결과가 아니다.

### 문서 충돌·누락·미결정 사항

- 개발기준 p.4는 실제 서비스 시험을 NOT_RUN으로 표시하는 반면, README는 health 검증의
  과거 성공 기록을 적고 있다. 둘은 범위가 다르다. health 성공은 스캐폴드 검증이고, 업무
  기능의 실제 시험은 여전히 미수행이다.
- 개발기준에는 여러 경로 예시가 있으나 p.4와 p.34는 논리 모듈·제안 경로가 실제 endpoint
  생성이나 공개 wire 계약을 뜻하지 않는다고 명시한다. 따라서 API 경로와 DTO 이름은
  미결정이다.
- 인증 방식과 USER/SESSION의 구체 schema, 물리 데이터 모델·FK·인덱스·격리 수준,
  활성 AI 계약/모드, 실패 진단의 암호화와 백업 삭제 증명은 미결정이다.
- 600초 동기 분석과 관련 운영 수치는 기술 제안이며, 실제 서비스 수준 목표나 구현 완료로
  간주하지 않는다.
- 문서의 A13 세 판단 필드와 일부 보류 JSON 확장은 A 채택 방향이지만, 정확한 schema·한도·
  계약 버전은 공동 확인 전 제안이다.

### Key Entities *(include if feature involves data)*

- **프로젝트**: 한 인증 사용자가 소유하는 작업 단위이며 A/B 쓰기의 공통 기준과 사용자
  진행 단계를 가진다.
- **기획 Profile**: 프로젝트의 10개 기획 값을 담는 현재 DRAFT 또는 CONFIRMED 상태다.
- **확인 사건**: 사용자가 전체 기획을 실제로 확정한 시점의 불변 snapshot과 행동 기록이다.
- **분석 시도와 Review**: 문서 분석 또는 구조화 기획 검토의 기준·결과·실패를 구분하는
  작업 이력이다.
- **개발자·환경 Profile**: 사용자가 선언한 역할, 책임, 숙련도, 환경·설치 지식 상태다.
- **Audit 사건**: 원문 없이 중요한 성공·거부·실패를 추적하는 최소 이력이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 수용 테스트에서 AI 제안만으로 CONFIRMED 또는 추천 기준이 생성되는 사례는
  0건이며, 모든 확정 사례는 사용자 전체 확인과 연결된다.
- **SC-002**: FR-A-002가 정의한 10개 기획 필드는 모두 허용 여부·출처·미정 의미를 검증할 수
  있고, 제외 3종 필드와 별칭의 저장·질문·추천 근거 사용 사례는 0건이다.
- **SC-003**: 권한 없음, 버전 충돌, 분석·Review 실패, 지연 응답 수용 테스트에서 기존
  CONFIRMED·성공 Review·확정 사건이 변경되는 사례는 0건이다.
- **SC-004**: A1-A15와 C1의 각 논리 데이터는 최소 하나의 요구사항과 하나의 수용 시나리오에
  연결되어 추적 가능하다.
- **SC-005**: 모든 성공 상태 변경 수용 테스트는 관련 Audit 존재를, 모든 실패 수용 테스트는
  부분 업무 저장이 없음을 확인한다.
- **SC-006**: 인증 주체가 확인되지 않았거나 프로젝트 소유자가 아닌 수용 테스트에서
  프로젝트 데이터·근거·상태 변경·Audit 대상 노출 사례는 0건이다. 로그인 제공자와 세션
  방식은 이 측정 기준의 범위 밖이다.

## Assumptions

- MVP의 프로젝트는 개인 소유자 중심이며 팀 초대·공동 편집은 이 명세의 범위 밖이다.
- 인증된 사용자 식별자는 제공되지만, 로그인 방식과 USER/SESSION의 상세 모델은 아직
  결정되지 않았다.
- AI·B·Frontend는 A가 제공하는 계약을 소비하며, A의 원천 데이터 저장소를 직접 변경하지
  않는다.
- 데이터 모델, ERD, 마이그레이션, 물리 삭제 방식, API 경로·DTO, 기술 설계, 기능 구현은
  후속 명세·계획의 범위다.
- PDF의 확정/제안/NOT_RUN 표기를 우선하며, 문서에 없는 요구사항은 이 명세에서 확정하지
  않는다.

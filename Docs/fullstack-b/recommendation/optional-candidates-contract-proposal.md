# FSB-04 선택 후보 분리 계약 제안

> 상태: **B 구현 완료, 팀 계약·실도구 승인 대기**. 2026-10-26 B는 명시적 `OPTIONAL` 근거가 있는 경우에만 선택 후보를 만들고, 기본 도구와 별도 API 배열로 반환한다. AI의 `OPTIONAL` 판정 정책과 프론트 노출·선택 흐름은 아직 합의·구현되지 않았다.

## 현재 확인된 동작과 누락

- B 엔진은 AI가 `REQUIRED`로 분류한 Capability를 덮는 검증된 최소 구성만 찾는다. 환경·고정 버전·의존성·충돌·포함 컴포넌트·정확한 조합 근거를 검사한다.
- `AiCapabilityIntake`는 `REQUIRED`·`OPTIONAL`·`UNDETERMINED`·`NOT_REQUESTED`를 받는다. `RecommendationInputAssembler`는 `REQUIRED` 집합과 미정 여부를 기본 추천 엔진에 전달하고, B의 별도 선택 후보 판정기는 근거가 있는 `OPTIONAL`만 사용한다. `NOT_REQUESTED`는 확인된 작업 입력에 신호가 없다는 뜻이며 선택 후보로 승격하지 않는다.
- PRD `FSB-04`와 추천 API 초안은 `RECOMMENDED` 결과에서 최소 기본 구성과 `required=false`인 선택 항목을 구분하도록 요구한다. B는 DB의 `required` 플래그와 API의 기본 `items`·별도 `optionalItems`를 연결했다. 선택 후보는 기본 구성과 정확한 조합이 검증된 경우에만 제안하며, 선택하지 않은 후보는 Preview·ZIP에 포함되지 않는다.

## 확정이 필요한 의미

기존 3값 분류에서는 언급되지 않은 8개 기능을 모두 `UNDETERMINED`로 처리해 추천이 막혔다. 네 번째 값 `NOT_REQUESTED`로 이 문제를 분리했지만, **필요하지 않음**과 **있으면 유용한 선택 기능**의 차이는 여전히 별도 판단이 필요하다. `NOT_REQUESTED`를 선택 추천으로 승격하면 사용자에게 불필요한 도구와 권한을 제시할 수 있다.

AI·Frontend와 다음 두 가지를 결정해야 한다.

1. 9개 전량 반환과 명시적 `NOT_REQUESTED`는 구현했다. `OPTIONAL`을 어떤 근거로 제안 가능한 선택 기능으로 판정할지, 또는 선택 제안 가능 여부를 별도 필드로 둘지는 팀 합의가 필요하다.
2. 프론트에서 `optionalItems`를 어떻게 표시하고 사용자의 명시적 선택을 받을지. 현재 프론트는 기본 `items`만 표시한다. `required=false`는 기본 설치·권한 승인·Preview 선택을 뜻하지 않는다.

## 제안하는 구현 순서

1. AI 성공 응답에서 필수·선택 제안·불필요·미정을 구별하는 계약과 근거 필드를 합의한다. 미정 또는 기획 충돌이 관련된 경우 `NEEDS_INFORMATION`을 우선한다.
2. B는 먼저 필수 Capability를 만족하는 최소 기본 구성을 판정한다. 선택 후보는 그 기본 구성과 **정확한 전체 조합**이 검증된 경우에만 별도로 탐색한다. 후보가 없거나 검증이 안 됐으면 선택 목록은 빈 배열이다. 이 B 경계는 구현·단위 검증했다.
3. 공개 응답은 기본 `items`와 `optionalItems`로 구분한다. B의 Preview는 사용자가 요청한 도구만 조합 검증·렌더링한다. 프론트의 선택 UI 연결은 남았다.
4. 인수 테스트에는 필수만 있는 경우, 선택 후보가 없는 경우, 단독 검증은 됐지만 기본 구성과 조합 검증이 없는 경우, 설치·권한·환경 변경 후 오래된 선택 후보 차단을 포함한다.

`NO_ADDITIONS_NEEDED`의 `items=[]` 불변 조건과 필수 중심 최소 추천은 유지한다. AI 계약·프론트 선택 UI·실제 승인 Catalog가 연결되기 전에는 `FSB-04`의 제품 완료로 세지 않는다.

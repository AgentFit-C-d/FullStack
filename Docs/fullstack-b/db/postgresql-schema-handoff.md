# Phase 1 PostgreSQL: B-owned schema handoff

Source: [AgentFit A·B Phase 1 development baseline](../../AgentFit_AB_1차통합_개발기준.pdf), pages 6 and 20–24 (B1–B9), page 35 (deletion). The source calls this a design, not tested DDL. [b-schema.sql](../../../services/core-api/src/main/resources/db/postgresql/b-schema.sql) is the first B-owned PostgreSQL DDL implementation of that design.

## Ownership and integration order

The baseline has 25 tables: A1–A15, B1–B9, and common C1 `audit_event`. The B script creates only the nine B tables. A owns `project`, `project_profile`, `profile_confirmation_event`, authentication/user tables, the common Audit transaction, and their migration order. Do not create placeholder A tables in the production migration. Apply the B script after A's three referenced tables exist. Once A's branch is merged, assign the script a migration version in the shared migration chain and wire the Spring datasource; it is intentionally not auto-run on the current B branch.

The Catalog remains an immutable verified file release. Its `catalog_release`, `catalog_hash`, `tool_key`, `support_key`, and `mapping_key` are **not** database foreign keys. B must recheck them against the exact approved release before storing or using a recommendation or Preview.

| Baseline | PostgreSQL table | Parent / purpose |
| --- | --- | --- |
| B1 | `recommendation` | A `project`, `project_profile`, `profile_confirmation_event`; immutable basis and four outcomes |
| B2 | `recommendation_capability` | Capability necessity, reason, permitted input paths |
| B3 | `recommendation_item` | Verified additional tool and support reference |
| B4 | `recommendation_notice` | Question or reason tied to the recommendation basis |
| B5 | `config_preview` | Content-free Preview digests and one approval bundle |
| B6 | `config_selection` | Tool chosen from a recommendation item |
| B7 | `config_permission_selection` | Reviewed mapping and policy |
| B8 | `config_preview_file` | Output path, action and hashes, no bytes or Diff |
| B9 | `config_export` | Generated ZIP metadata and latest user report |

## What the DDL enforces

UUID primary keys, parent foreign keys, required values, nonnegative basis versions, fixed status/policy enums, lowercase 64-character SHA-256 hashes, unique recommendation tools and Preview paths, question/reason shape, approval timestamp bundle, Preview file action/hash shape, and report state/reason shape. The script has no `ON DELETE CASCADE`: page 35 requires an authenticated, project-locked deletion transaction in a specific child-first order. `approved_by` and `reported_by` become physical user foreign keys only when A's authentication table name is known.

## What the Spring transaction must enforce

1. Lock and owner-check A's `project`; read one consistent confirmation event, profile, role/environment versions, and current Catalog. Check that the event and mutable profile belong to the same project and that the event's confirmed ID/version and project version match the saved recommendation basis. Do **not** join the mutable profile to reconstruct an old recommendation.
2. Before committing a recommendation, check the status-dependent child counts and all nine Capability decisions. Store B1–B4 and a success Audit event atomically with an A `saveIfUnchanged` comparison.
3. Before committing a Preview, verify its recommendation is CURRENT and RECOMMENDED; each selected item belongs to that recommendation. Check exact installed versions, dependencies, conflicts, full Capability coverage, support/policy mapping, generated paths and fingerprint. Store B5–B8 and Audit atomically. Never persist original file bytes, generated bytes, ZIP, or Diff.
4. Fill B5's approval bundle at most once with a conditional update or row lock. Verify owner, current basis, Preview expiry and submitted fingerprint, then write Audit in the same transaction. Regenerate ZIP only from the still-approved Catalog release.
5. Insert B9 only after regeneration/fingerprint checks; save generation metadata and Audit atomically before returning ZIP bytes. On a user report, lock B9, replace only its latest report fields and write the historical Audit event in that transaction. The report remains a USER statement, never proof of installation.
6. On project deletion, follow the baseline's child-first order, remove project Audit and B rows before their A parents, then verify a late recommendation/Preview/export cannot write against the deleted project.

The cross-project event/profile relation, selected item's membership in the Preview's recommendation, state-dependent child counts, source field allowlist, Catalog references, and concurrency cannot be proven by these single-column foreign keys alone. They remain **open integration checks**, not silently satisfied by the DDL.

## Local PostgreSQL and verification status

Run `docker compose -f infra/postgres/compose.yaml up -d --wait` from the repository root. The development server is reachable only at `127.0.0.1:5433`, with database/user `agentfit`. The Compose file's default password is for this local-only instance; set `AGENTFIT_LOCAL_DB_PASSWORD` before first startup if a different local password is desired. The named volume preserves data across container restarts. Use `docker compose -f infra/postgres/compose.yaml stop` to stop it without deleting data.

Run `./infra/postgres/verify-b-schema.ps1` to exercise B's DDL against the container's real PostgreSQL engine. The script creates minimum A parent tables and all nine B tables **inside one rolled-back transaction**, inserts a valid B1–B9 chain, and rejects invalid status, partial approval, incomplete reports/questions, and an absent parent. It leaves the `agentfit` database untouched. On 2026-10-11 this passed on PostgreSQL 17.11; the container remained healthy at `127.0.0.1:5433` afterward. The test also caught and fixed a PostgreSQL `CHECK`/`NULL` three-valued-logic hole in the report and question constraints.

The B-only `JdbcPreviewMetadataWriter` accepts an A-owned JDBC transaction after a Preview has been validated. It checks the stored B1 recommendation basis/status and B3 item membership, then inserts B5–B8 without file content or Diff. `JdbcPreviewApprovalWriter` locks that B5 row, checks its stored fingerprint/times and B1 basis/status, and conditionally fills the approval bundle once. Both writers leave commit/rollback and Audit to A. Their opt-in PostgreSQL test uses temporary A parent stubs, writes a full B5–B8 chain, checks stored fields, rejects changed basis/missing required items/reapproval, and rolls back all tables. Run it with `AGENTFIT_TEST_POSTGRES_URL=jdbc:postgresql://127.0.0.1:5433/agentfit` (plus optional `AGENTFIT_TEST_POSTGRES_USER` and `AGENTFIT_TEST_POSTGRES_PASSWORD`) before `mvn -Dtest=JdbcPreviewMetadataWriterTest test`. Without that environment variable, the Docker-dependent test is skipped during ordinary builds.

Before its first insert, the Preview writer also recomputes B5's three canonical hashes from the content-free Draft and rejects inconsistent supplied digests. This prevents an invalid Preview from being stored only to fail later at approval. It does not verify live Catalog support or A's current version basis; those are checked at the upstream workflow and A transaction boundary.

Because `existing_state` is not an input to the agreed fingerprint, B also checks it separately against B8 actions at insertion and approved-context read: `PROVIDED` requires an UPDATE, while `UNKNOWN` and `USER_SAYS_EMPTY` cannot have one. This catches a contradictory stored state, but does not make two otherwise identical no-original states cryptographically distinguishable; approved rows still require A's immutability policy.

`JdbcRecommendationMetadataWriter` accepts an explicit B1–B4 Draft in A's caller-owned transaction. It rejects a missing/duplicate Capability, tool rows for non-RECOMMENDED outcomes, and missing question/reason rows for outcomes that require them before inserting. Its opt-in PostgreSQL test uses rolled-back A parent stubs. The Draft is intentionally not fabricated from the current AI/Catalog workflow: B3's required/optional choice and B4's user-facing reason/question text still need the A·AI response contract. A must verify current ownership and versions, map an independently approved Catalog/validated AI result, append Audit, and commit or roll back the entire chain.

`JdbcLatestRecommendationReader` reads the latest B1 row and its ordered B3 tool keys inside A's authenticated project transaction. It returns the immutable basis and stored outcome for the existing CURRENT/STALE read model, or null when no recommendation exists. It does not read A's current versions or perform owner checks itself; A must supply those before exposing a response.

`JdbcConfigurationExportWriter` takes the content-free history produced after ZIP regeneration. In the same caller-owned transaction it locks B5, checks approval ID/time/fingerprint, B1 basis/status, and the exact B8 file path/action/hash set before inserting B9. It never stores ZIP bytes. The opt-in PostgreSQL test verifies a generated export and rejects a changed B8 file hash. A must still check ownership and current A versions, append Audit, commit, and only then release ZIP bytes to the caller.

`JdbcStoredPreviewReader` reads B5 by Preview ID or approval ID, joins the immutable B1 basis, and returns stored Preview and optional approval metadata only for the project ID passed by A. Its caller must already have authenticated and locked that project; the project filter itself is not an owner check. A must separately provide current versions and Environment, then recheck expiry and fingerprint through B's approval/download workflow.

`JdbcConfigurationReportWriter` updates only B9's latest USER application statement. It locks the export row, rejects a report before ZIP generation or at/before the preceding report time, and saves report ID, state, allowed reason, authenticated actor, and server time. The B9 table also rejects a `reported_at` earlier than `generated_at`, even if a caller bypasses this writer. A must check export ownership and write each historical report to common Audit in the same transaction; B9 alone intentionally retains only the latest statement. APPLIED must not be interpreted as verified installation.

`JdbcConfigurationHistoryReader` joins B9/B5/B1 and reads B8 file metadata to restore content-free generated history and the latest USER report. It scopes the lookup by the project ID supplied by A, rejects a changed export fingerprint, and never reads configuration bytes or Diff. The B domain restore boundary validates IDs, basis, file paths, and hashes. A still supplies the authenticated current basis and historical Audit association before exposing the read model.

`JdbcLatestRecommendationReader.latestMetadata` now restores the full persisted B1–B4 result, including all nine Capability rows, tool versions/support keys/reasons, and question/reason notices. It validates the same outcome shape as the writer, so A can assemble the latest response without another AI request. A must still authenticate, obtain the current basis, and attach only permissions/support from the independently approved Catalog before public response mapping.

`JdbcLatestRecommendationReader.byId` also selects B1/B3 by exact recommendation ID and project ID inside A's transaction. A can use the recommendation ID from `JdbcStoredPreviewReader` to restore the Preview's own selection even after a newer recommendation exists. Neither reader supplies A's current Environment target or installed-version map.

`JdbcConfigurationContextReader` combines those two B reads by Preview or approval ID in the same caller-owned transaction and checks that the recommendation basis matches the stored Preview basis. It returns no context for a missing or foreign ID. This supplies only saved B facts to A's trusted download adapter; A must separately authenticate and lock the project, read current basis and Environment/installed versions, enforce freshness, write Audit, and commit generation metadata before sending ZIP bytes.

The context reader also locks B6–B8 rows and recomputes B5's selection, content, and final fingerprints from tool choices, permission policies, generator version, and file path/action/hash metadata. This detects a changed stored policy or file target without loading configuration bytes. The digest check does not replace A's approved-record immutability rule or its atomic current-state check at export commit.

`JdbcPreviewApprovalWriter` invokes the same metadata integrity read under its B5 row lock before filling the approval bundle. A changed B6/B7/B8 record therefore cannot receive a new approval ID even if B5's original fingerprint is still present. A still checks current project versions and writes Audit in the same owner-checked transaction.

Its `list` method returns 1–100 generations per page, ordered by `generated_at DESC, id ASC`, with a keyset cursor from the last returned row. The DDL includes a matching B9 order index. A must authenticate and authorize the project, encode/decode the cursor for HTTP, and apply the owner-checked current basis to each item. The B reader does not turn a USER report into verified installation.

`ConfigurationHistoryPageService` now projects such a stored page against one A-provided current basis and preserves per-item CURRENT/STALE and latest USER report without changing verification status. A maps the JDBC `Cursor`/`Snapshot` into its owner-checked `PageReader`, ensures basis and page belong to one consistent transaction, and encodes the cursor opaquely for HTTP. The B service rejects foreign generations, wrong order, or a next cursor that does not match the final returned row; it does not authenticate or expose an endpoint itself.

`JdbcProjectBDataDeleter` removes B9, B8, B7, B6, B5, B4, B2, B3, then B1 for one project in foreign-key order. It neither authenticates the caller nor deletes A rows or common Audit. A must lock and owner-check the project, delete its Audit and A rows in the agreed order, and commit once; otherwise roll back all B deletes. The opt-in PostgreSQL test verifies a full B chain is removed while another project's recommendation remains. A's real cross-table migration and late-write race checks remain pending.

A two-connection PostgreSQL test also confirms that an active B9 history read blocks B-row deletion until the read transaction releases its share locks, then deletion can be retried. This covers read/delete serialization only. A's project-row lock and its late-write/deletion race test are still required.

A second two-connection test confirms that competing USER report writes serialize on B9's row lock. Once a newer report commits, an older report time is rejected and the latest APPLIED statement remains. A must still authenticate the actor and append each historical report to common Audit atomically.

`JdbcConfigurationExportWriter` now holds B8 file rows with `FOR SHARE` while comparing them to the generated ZIP metadata and inserting B9. A concurrent B8 hash update cannot change the checked values before commit. The approved B8 rows must remain immutable after commit through A's migration/write policy; the lock alone does not enforce that longer-lived invariant.

The export writer also invokes the B5–B8 metadata integrity read immediately before inserting B9. A policy choice changed between the earlier download-context lookup and the save now rejects the export. This B check does not establish A's current versions or commit the caller-owned transaction.

The running `agentfit` database intentionally has no A/B application tables yet. A's real schema and migration ordering, the authenticated adapter that passes its locked transaction to B, current A version recheck, Audit, deletion, and public API remain **NOT_RUN**. Do not mark B05, B10, or B12 complete from this B-only JDBC test.

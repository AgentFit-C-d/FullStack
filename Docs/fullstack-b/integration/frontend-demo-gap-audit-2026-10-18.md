## 가장 큰 데모 위험

1. **서로 다른 두 화면의 오인:** `/demo/projects/...`의 10단계는 메모리 시연이다. 실제 API 경로 `/app/projects/:id/...`는 각 단계 디자인 화면 대신 `/app/live?project=id` 한 화면으로 이동한다. 발표 시 디자인 화면에서 DB 저장·추천·ZIP까지 되는 것처럼 보여주면 실제 기능과 다르다.
2. **실제 도구 추천 오인:** 현재 추천·ZIP은 데모 Catalog를 사용한다. skills.sh 후보를 받아왔다고 곧바로 안전한 설치 도구로 추천하지 않는다.
3. **분석 재시도:** 첫 분석 전 자료 저장 상태는 화면에서 복원한다. 분석 완료·실패 뒤 원문은 삭제된다. 이후 새 자료를 저장하고 새로고침한 경우에는 A의 응답 계약만으로 이전 분석 자료와 새 자료를 구별하지 못하므로 같은 화면에서 분석하거나 다시 업로드해야 한다.
4. **AI 원문 근거 검증:** Solar가 원문에 없는 인용을 반환하면 `INVALID_PROVIDER_OUTPUT`으로 실패한다. 한국어 1페이지 PDF·명확한 Markdown은 성공했지만 영문 PDF 일반 동작은 입증되지 않았다.

## 후속 우선순위

1. 서비스의 단계별 디자인을 실제 API 상태에 연결할지, `/app/live`를 데모의 공식 화면으로 쓸지 결정하고 발표 동선을 하나로 고정한다.
2. 이전 분석 이후 새로 저장한 기획 자료의 분석 가능 상태를 복원하려면 A 응답에 현재 입력 revision과 최근 분석의 입력 revision 또는 원문 보존 여부를 제공하도록 협의한다.
3. 실서비스 역할·환경 필드와 B 계약을 제품 요구사항에 맞춰 좁혀 확정한다. 프론트 시연 필드를 그대로 저장 필드로 간주하지 않는다.
4. 실제 도구의 OS·Client·권한·설정 출력을 검증해 Catalog에 승인하고, 비추천·추가 질문·실패 및 적용 보고 경로를 브라우저에서 별도 확인한다.

## 2026-10-19 Docker 전체 경로 재검증

## 2026-10-19 추천 응답 계약 후속 검증

추천 생성 `POST`는 AI 질문 목록을 반환하지만 저장된 B 질문·사유 코드는 반환하지 않는다. 반면 `GET /recommendations/latest`에는 저장된 `notices`와 `validity`가 포함된다. 생성 직후에도 최신 저장 결과를 다시 읽도록 프론트를 수정해 새로고침 전후 안내를 일치시켰다. 안내는 `environment_target`, `installed_components`, `installed_component_version`, `undetermined_capability`, `pending_conflict` 질문과 호환 불가·추가 도구 불필요 사유 코드를 구분한다.

브라우저에서 QA 프로젝트 `f8c78fc7-e063-49e2-af48-3dd3bdd723b9`의 설치 목록을 `미확인`으로 바꾼 뒤 생성한 결과는 `NEEDS_INFORMATION`이며, 생성 직후 `설치 도구 목록을 확인해 주세요` 안내와 저장된 질문 1건이 표시됐다. 검증된 데모 도구 `demo-all-capabilities-skill` 버전 `demo-1`을 설치된 것으로 선언한 결과는 `NO_ADDITIONS_NEEDED`와 `이미 설치된 검증 도구` 안내였다. 이후 테스트 환경을 원래의 `설치 목록 확인됨·빈 목록`으로 복구하고 `RECOMMENDED · CURRENT`를 다시 생성했다. 이번 프론트 수정 기준 `npm test` 90/90, lint와 빌드가 통과했다.

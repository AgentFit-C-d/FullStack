# 중간 발표 이후 진척: 새 주제 2장

기존 발표의 프로젝트 맞춤 추천 흐름, 카탈로그 구조, 권한·Preview 설명과 겹치지 않도록 **실제 연동에서 발견한 계약 문제**와 **실물 후보의 검증 범위**에 집중한다. 현재 코드와 검증으로 확인한 사실만 사용한다.

## 슬라이드 1 — AI 서버 교체 전, 응답의 의미부터 맞추기

**화면 문구**

- 별도 AI는 검색용 `needs[]`를 반환, B 추천은 9종 Capability 판정을 사용
- B에 Bearer 인증·마감 시각·예산 lease·근거 ID 변환 클라이언트 구현
- 검색어를 필수 기능으로 자동 승격하지 않고 계약 오류를 분리
- 남은 연결: A의 예산 lease와 AI의 필수·선택·미정 판정 계약

**발표 대본**

“기능을 연결하면서 같은 ‘필요 기능’이라는 말에도 두 서버의 데이터 의미가 다르다는 점을 확인했습니다. 별도 AI는 Skill 검색에 쓸 키워드를 보내지만, B는 그 기능이 필수인지 선택인지와 근거를 알아야 추천을 판정합니다. 그래서 검색 결과를 곧바로 필수 기능으로 처리하지 않고, 별도 AI 형식의 요청과 응답을 받는 경계를 따로 구현했습니다. 현재 이 경계의 로컬 HTTP 테스트는 통과했고, 실제 추천으로 연결하려면 A의 예산 lease와 AI의 Capability 판정 계약이 더 필요합니다.”

**도식 제안:** 왼쪽 `확정 사실` → 가운데 `검색 needs[]` → 오른쪽 `추천 판정에 필요한 9종 Capability`. 가운데와 오른쪽 사이에 `의미 계약 확정 필요` 표시. 추천 엔진 전체 흐름도는 다시 그리지 않는다.

## 슬라이드 2 — 실물 Skill의 지원 범위를 증거로 제한하기

**화면 문구**

- skills.sh에서 받은 TDD Skill을 파일 해시로 고정
- Windows + Claude Code `2.1.310`에서 테스트 작성 기능만 로컬 검증
- 편집·테스트 실행 권한은 `ASK` 또는 `DENY`; 위험도는 `MEDIUM`
- 단일 Skill 구성만 확인, 복수 도구 조합과 테스트 실행 기능은 미검증
- 후보 검증기 통과, 팀 독립 승인 후 운영 반영

**발표 대본**

“외부 디렉터리에 Skill이 있다고 해서 바로 추천에 넣지 않았습니다. 파일을 고정하고 로컬 Claude Code 버전에서 어떤 작업이 실제로 가능한지 확인했습니다. 이 Skill은 테스트 작성을 돕는 증거가 있지만, 테스트 실행을 독립적으로 제공한다거나 다른 도구와 함께 동작한다는 근거는 없습니다. 권한과 위험도도 따로 기록했고, 현재 후보의 무결성·형식 검사는 통과했습니다. 팀의 별도 승인이 남아 있어 운영 추천에는 아직 넣지 않았습니다.”

**도식 제안:** `고정 파일/버전` → `단독 실행 근거` → `권한·위험도 기록` → `독립 승인 대기`의 짧은 증거 체인. 수많은 Skill을 모두 저장했다는 표현은 사용하지 않는다.

## 발표 전 확인

- 별도 AI 클라이언트가 **추천 생성 API에 아직 연결되지 않았음**을 유지한다.
- 새 후보 해시 `e220a4a01e8865779c78464e722dbb24dff112c7e44475c284a54c4316661527`는 파일 무결성 값이며 독립 승인 값이 아니다.
